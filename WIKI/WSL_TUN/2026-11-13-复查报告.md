### 建议优先完善

1. **为 Claude 制定明确的启动入口。** 如果希望它始终采用选定代理，应在同一终端先设置代理并确认连通性，再启动 Claude。可以后续增加一个专用启动包装函数，在代理检查失败时停止启动。当前尚未添加。
2. **区分设置变量成功与网络验证成功。** 当前 `xq_proxyon` 在变量设置完成后，即使公网查询失败也可能返回 0，所以简单写 `xq_proxyon && claude` 不能作为强制连通性保障。若增加启动包装函数，应单独检查网络结果；不要假定现有返回码已经实现这个保证。
3. **明确控制范围。** shell 的 HTTP 代理变量不是全系统流量限制，不会自动影响其他终端、已运行程序、所有后台服务或 Windows 浏览器。关闭代理后直连仍然可用。若有后台任务需要相同连接方式，应在其实际服务环境中配置。

Claude Code 官方说明：shell 环境变量在启动时读取，另一个终端的环境变化不会改变既有进程。设置文件中的变量也有作用域和启动时机差异，修改后应按对应文档重新启动验证。[官方网络说明](https://code.claude.com/docs/en/network-config)

## WSL 互操作检查标准更正

实际运行环境中观察到：

```text
/etc/wsl.conf:
  interop.enabled=false
  interop.appendWindowsPath=false

Windows PATH：无
WSL_INTEROP 环境变量：未设置
/proc/sys/fs/binfmt_misc/WSLInterop：仍显示 enabled，interpreter /init
/run/WSL：仍可见 1_interop、2_interop 套接字名称
```

这些结果并不矛盾。微软实现中，WSL2 的 binfmt 处理器在整个 VM 层面注册；某个发行版是否可以启动 Windows 程序，还取决于它的配置和连接 Windows 的 interop 通道。`Config.InteropEnabled=false` 时不建立该通道；创建进程请求只有在通道有效时才转发。

因此，之前“注册项应不存在或禁用”的判断过于简单，现已更正。注册项、环境变量、套接字名称均不能单独作为全部功能允许或禁止的证明。

当前配置、重启时间和 PATH 状态符合预期；遵守用户要求，本次没有运行任何 Windows 程序做执行测试，也没有擅自修改共享 binfmt 注册。保留磁盘共享和网络访问也意味着这不是与 Windows 完全隔离的独立 VPS。

依据：[微软互操作技术说明](https://wsl.dev/technical-documentation/interop/)、[微软 WSL 初始化源码](https://github.com/microsoft/WSL/blob/master/src/linux/init/config.cpp)。

## 仍然存在但与地区设置无关的限制

- Codex 配置请求 1,000,000 token 上下文、500,000 token 自动压缩。当前模型目录中的 `gpt-6-astra` 上限仍为 872,000，窗口会按模型上限限制，500K 阈值兼容。没有证据说明这些数值是本次刚从后端更新的目录数据。
- 非交互式脚本可能继承调用者传入的 LANG/LC_*。`.bashrc` 的交互判断会提前返回；若后台任务明确传入 `LANG=C.UTF-8`，它可以继续使用 C.UTF-8。这是环境变量优先级，不代表系统默认语言失效。
- 显式设置 `LC_ALL=C` 或 `TZ=Asia/Shanghai` 的单个命令仍可以覆盖默认值。无需用永久强制 LC_ALL 来禁止正常的命令级覆盖。
